# UI-R4 Timetable Interaction Addendum Implementation Roadmap

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkboxes for tracking.

**Goal:** Implement the approved UI-R4 addendum through four independently reviewable subplans while preserving the existing timetable vertical geometry and all school/manual persistence semantics.

**Architecture:** Pure state and projection helpers establish semester-end, gesture, SCHOOL-ghost, detail-page, palette, wallpaper, and rail-width behavior. ## Cross-plan compatibility contracts

1. `WeeklyTimetableLayout.place` remains the only overlap-column algorithm. SCHOOL ghosts selected for marker attachment are removed before the existing joint SCHOOL/MANUAL placement; active SCHOOL, MANUAL, and unattached SCHOOL ghosts still enter that one placement call.
2. `TimedBlock.colorKey` remains the stable course identity for school blocks and stable palette key for all blocks. No display-name comparison is introduced.
3. `TimetableWeekPageUiState` carries marker metadata keyed by `SchoolCanonicalPresentationKey`; local `MeetingId` is used only to resolve click/detail content and never participates in attachment choice or order. `PlacedBlock` and `TimedBlock` remain persistence-free layout types.
4. Existing `courseDetailsByMeetingId` remains the complete-arrangement lookup source. The pager projection selects anchors by canonical presentation key and uses the selected local ID only after ordering, without changing domain meetings.
5. Palette identity and generated tones are separate: seed plus `colorKey` chooses an index; resolved appearance chooses light/dark container and on-container colors.
6. Wallpaper visibility is consumed only by `AppBackgroundLayer`. `CoursePalette.alphaFor` remains solely the current/non-current-week policy.
7. Measured rail width changes only horizontal allocation. All calls to `axis.fractionOf`, `SegmentedTimelineAxis.resolve`, and `LongPressResolver.resolve` retain their existing inputs and behavior.
